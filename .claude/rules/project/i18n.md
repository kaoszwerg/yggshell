# Every word the user reads comes from the catalogue

The interface speaks English and German. English is the **default** and the **source**: a message is
written in `src/i18n/en.ts`, and `de.ts` is typed against it.

## Adding a message

```tsx
// 1. src/i18n/en.ts — the source
"settings.font.label": "Font",

// 2. src/i18n/de.ts — the compiler already refuses to build without this
"settings.font.label": "Schriftart",

// 3. the component
const t = useT();
<span>{t("settings.font.label")}</span>
```

Keys are flat, `area.thing.part`. Flat because "does every language have every key" is then a
one-line check, and because a key stays greppable.

## Two gates, and what each one catches

- **The compiler** catches a message that exists in English and not in German — `de.ts` is
  `Record<MessageKey, string>`, so a missing key does not build.
- **`i18n/no-untranslated-text`** (in `check:all` via `eslint.config.project.mjs`) catches the other
  direction: a string written straight into a component. Without it the interface drifts back into
  English one new button at a time, and *no type could object* — an English word in JSX is a
  perfectly good string.

It checks JSX text and the props that end up on screen (`label`, `tooltip`, `placeholder`,
`aria-label`, `description`, `emptyHint`, `addLabel`, `title`).

## What is deliberately NOT translated

- **What a program prints.** Sample terminal output, compiler messages, shell paths. `cargo build`
  says `error: could not compile` on every machine; translating it in a preview would misrepresent
  what the user is about to see. Wrap it in `<code>`/`<pre>`/`<kbd>` — that says so to the reader
  *and* to the gate.
- **Technical terms, inside German sentences**: tmux, Git, Branch, Commit, Diff, Shell, Powerline,
  WebView. The people using this app read those words in their tools all day.
- **A name that is identical in both languages** still goes in the catalogue (`common.devChannel`),
  so the decision is visible rather than an English string that happened to slip past the check.

## Where the language lives, and why in two places

`settings.json` holds it — it is a preference like any other, and it must survive a `localStorage`
reset. The UI store **mirrors** it (`useUiStore.locale`), and `useSyncLocale` at the app root keeps
the mirror equal to the setting. Two reasons, both load-bearing:

- **The first frame.** Settings arrive over IPC. Reading them directly means the whole interface
  paints in English and then switches — a visible flicker on every launch.
- **Leaf components.** `t()` is used inside primitives; sourcing it from a query would drag a
  `QueryClientProvider` into each of their tests, for a value that changes about once in a user's
  life.

The direction is never ambiguous: **`settings.json` wins**, the mirror only makes it fast.

## The last-resort screens do not use the hook

`FatalScreen` and the crash path call `localeOutsideReact()` instead. They run when React has already
failed — possibly inside the very store a hook would subscribe to — so they read the language
defensively and fall back to English. A crash screen that crashes tells the user nothing
(rule:crash-handling).

## Adding a third language

`src/i18n/xx.ts` typed as `Translations`, an entry in `LOCALES`, and a case in `isLocale`. The
compiler then lists every message that is missing. Nothing else in the app changes — that is what the
flat catalogue and the typed key buy.
